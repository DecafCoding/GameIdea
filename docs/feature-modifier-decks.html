Feature — Three Modifier decks

2026-11-02 · Extends GameIdea (working name), as planned in mvp-plan.html. Written from the /dev-add-feature run. Updated 2026-11-02 by /dev-ui-update.

Visual authority: design-system.html holds the Modifier color, the 3 icons, the rail row and the combine zones (sections 4.4, 7, 8.2 and 9.8). Where this brief and the design doc disagree on a visual detail, the design doc wins.

Summary and motivation

The one Modifier deck becomes 3 Modifier decks: Role, Resource and Setting. Each deck draws only modifiers whose targets list includes that deck. A modifier that fits more than one target is in more than one deck. For example, "cursed" is in all 3 decks.

The user gets an adjective that suits the card they want to change. Today one deck mixes 503 modifiers. Of these, 300 fit a Player Role, 245 fit a Setting and 189 fit a Resource. A random Modifier draw for a Resource card often gives words that do not fit.

The decks guide the draw only. For creative reasons, a modifier from any of the 3 decks can merge with any Player Role, Resource or Setting card.

The feature also fixes the On Top rule. A base card holds at most 1 merged adjective ring. A second Modifier sits on top as its own card.

Fit with the existing application

This feature changes one part of the core loop: step 4 in mvp-plan.html, the Modifier combine. It also answers 2 open questions about Modifier targets. One is in the Assumptions of mvp-plan.html. The other is in the Open questions of architecture.html.

No app code exists yet. The feature lands in M2, with the Modifier combine work. Related docs: mvp-plan.html, architecture.html, competitive-scan.html. The deck library is docs/libraries/modifier.md and the Modifier key in docs/libraries/decks.json.

Scope

In this feature

  • 3 Modifier decks: Role, Resource and Setting. Each draws from modifier.json, filtered by targets.
  • A modifier is in every deck that its targets list. It can be in 1, 2 or 3 decks.
  • A modifier from any of the 3 decks can merge with any Player Role, Resource or Setting card.
  • A Modifier card shows the icon of its deck. A merged ring and a card made by Split or swap keep that icon.
  • A base card holds at most 1 merged adjective ring.
  • On Top: a second Modifier sits on top of a merged base card as its own card. It moves with the base card and reads in the hook. A base card takes 1 on-top Modifier.
  • The left rail has one "Modifiers" group with 3 icon buttons and a hover label on each.
  • The M2 pass bar counts each Modifier deck: 20 usable of 25 draws.

Deferred

  • A Modifier on Mechanic or Mood cards. This stays deferred, as in the MVP plan.
  • More than 1 on-top Modifier on a base card
  • Genre tags on Modifier cues. The 3 Modifier decks ignore the genre settings (the Genres tab in Settings from Phase 6).

Never

  • A rule that a modifier can merge only with the card type of its deck. The user wants any modifier to fit any of the 3 base cards.
  • More than 1 merged adjective ring on a base card (no rings[2])

Data model changes

Card
  type: ... | modifier | ...       (unchanged: one Modifier type)
  modDeck?: role | resource | setting
                                   required on a modifier card. The deck that drew it.
  rings: Ring[]
    role, resource, setting:       rings[0] = 4 cues.
                                   rings[1] = 4 adjectives, only after a combine.
                                   There is never a rings[2].
  onTopOf: Card.id | null          a modifier card on top of a merged base card.
                                   null on every other card.

Ring
  cues: Cue[]
  activeIndex
  modDeck?: role | resource | setting
                                   set only on a merged adjective ring.

Pool (modifier.json)
  type: modifier
  cues: { id, text, targets }[]    targets: 1 or more of role | resource | setting.
                                   Required in modifier.json. Absent in the other pools.

Rules

  • A Modifier draw uses only cues whose targets include the button's deck. The card stores that deck in modDeck.
  • A card stores a copy of its cues. It does not store targets.
  • The first combine moves the Modifier's ring into rings[1], copies its modDeck to the ring, and deletes the Modifier card.
  • Swap gives the old ring to a new Modifier card beside the base card, with the ring's modDeck. The new Modifier's ring takes rings[1].
  • On Top sets the second Modifier's onTopOf to the base card. The Modifier stays a card. It moves with the base card.
  • Split moves rings[1] into a new Modifier card beside the base card, with the ring's modDeck. An on-top card stays on top.
  • A drop on a base card that has no merged ring always merges. This is true when an on-top card is already there.
  • Discard of a base card treats its on-top card the same as its tucked cards.

Hook sentence

On a base card, the active text is the on-top adjective, then the merged adjective, then the noun. A missing part is left out.

Migration and rollback

No app code and no saved boards exist. The new fields go into the first board format version, so there is no migration. The pool change is a change to the split before it runs. Rollback means a change to the plan only.

Interfaces and contracts

Left rail

The Modifier group becomes "Modifiers", with 3 icon buttons in this order: Role, Resource, Setting. All 3 use the Modifier color. The icon tells them apart. Each button has a hover label with its deck name. The rail order stays Hook Card, Core, Modifiers, Optional, Genres.

Example

  1. The user draws "pilot" and 2 Modifiers, "tall" and "frozen".
  2. The user drops "frozen" on "pilot". The card reads "frozen pilot", and an adjective ring is added.
  3. The user moves "tall" over the card. A dotted circle shows the swap zone, and a dotted section at the top shows the add-on-top zone.
  4. The user drops "tall" on the top zone. The hook reads "tall frozen pilot".

Pool contract

The split writes targets on each Modifier cue as kebab-case values: role, resource, setting. Each value has at least 20 cues. Today the counts are Role 300, Setting 245 and Resource 189.

Architecture fit

Outcome 1: it fits. The feature uses the existing pattern, layout, storage and boundaries.

  • pool-files: still 11 JSON files, one for each deck. The split already copies targets into the modifier pool. The 3 decks filter one file, the same as the genre filter in the 4 genre-tagged decks.
  • schema-shape: the new fields are optional fields on Card and Ring inside the Board record. No new table.
  • board-file-format: the new fields go into the first format version.
  • module-layout: the changes stay in features/draw/, features/card/, features/canvas/ and features/hook/.
  • hook-sentence: the sentence builder stays a pure function. It gets the on-top adjective as data.
  • undo-history: combine, swap, On Top and Split are state changes. Undo covers them.

Reasoning kept: the user asked why targets should differ from genre tags. No reason was found, so one file with a filter replaced 3 files. This removes duplicate cues and a sync test.

architecture.html still lists "How the app uses Modifier targets" as an open question. This brief answers it. /dev-architecture owns that file and can close the question.

Compatibility and rollout

No code, no users and no saved boards exist. There is no backward compatibility to keep and no feature flag. The feature ships in M2 with the rest of the Modifier work.

Build plan

All tasks land in M2: Hook test.

  1. Split: copy targets as kebab-case values. Add the 20-cue check for each Modifier deck. This proves first that the small Resource deck has enough cues.
  2. Data model: modDeck and onTopOf on Card, modDeck? on Ring, and the Zod import check.
  3. Draw: the 3 rail buttons and the target filter.
  4. Card: the deck icon from modDeck, for the card and the merged ring.
  5. Combine, swap and Split with modDeck.
  6. On Top: the drop zones, the onTopOf link, the move with the base card, and the 1-on-top limit.
  7. Hook: the reading order for the on-top adjective.
  8. The M2 pass bar run.

Done criteria

  • Each of the 3 Modifier buttons draws only cues whose targets include its deck. A unit test checks this on modifier.json.
  • Each Modifier deck has at least 20 cues. The split and a unit test check this.
  • Each Modifier card shows its deck icon. A merged ring and a Split card keep that icon through modDeck.
  • The example works: "frozen" merges into "frozen pilot". "Tall" on the top zone gives "tall frozen pilot". "Tall" on the center zone swaps, and "frozen" appears beside the card.
  • A base card takes 1 merged ring and 1 on-top Modifier. A third Modifier shows the swap zone only.
  • Split with a card on top leaves "tall" on top, and the hook reads "tall pilot".
  • The on-top Modifier moves with its base card. It survives Redraw, save, reload, and board export and import.
  • The M2 pass bar passes: 20 of 25 usable in each Modifier deck, and 12 of 20 hooks the user would build.

Open risks and assumptions

Risks

  • The Resource Modifier deck is the smallest: 189 cues, 115 of them for Resource alone. Its draws may repeat more than the other decks. The M2 pass bar tests it.
  • Hooks get longer. A full hook now takes 7 to 10 cards. The hook bar stays at 12 of 20 hooks the user would build.

Assumptions

  • The 3 icons and the Modifier color (#6E48B5, shared by all 3 decks) are recorded in design-system.html sections 4.4 and 7.
  • Discard of a base card treats its on-top card the same as its tucked cards. The user did not pick this. It follows the existing tuck rule.
  • The plan still counts 11 decks and 11 pool files. The Modifier deck draws as 3 decks from one pool file.
