Feature — Settings and theme

2026-11-02 · Extends GameIdea (working name), as planned in mvp-plan.html. Written from the /dev-add-feature run. Updated 2026-11-02 by /dev-ui-update.

Visual authority: design-system.html holds every token value, size and screen spec for this feature (sections 4, 8.2 and 9.11). Where this brief and the design doc disagree on a visual detail, the design doc wins.

Summary and motivation

A Settings dialog gives the user 3 settings: Mode (Dark or Light), Theme color (Orange, Blue or Green) and Snap to grid (on or off). The dialog also lists the keyboard shortcuts and shows the app version. The settings apply to every board in the browser. A change applies at once.

The reason is polish before other people use the app. The public site stays deferred, so "other people" means people who use the LAN build at port 4444. A new user can find the ring keys in the Keyboard list. A new user also gets a tidy board with no setup, because snap is on by default.

The feature also records 3 rail changes from the same mockups: an Add note button, a genre count line under Genres, and genre counts on the 4 genre-tagged deck buttons.

Fit with the existing application

The feature does not change the core loop. It adds one dialog beside it and changes how the canvas places a dropped card or note.

It reverses 2 rules of the inherited TheForge design: "one theme, no light theme and no theme switch", and "one accent, ember orange". The new rule is one accent at a time, chosen by the user. Warnings keep a fixed warm color.

No app code exists yet. The work lands in M5, with one guard rule in M1. Related docs: mvp-plan.html, architecture.html, competitive-scan.html, feature-modifier-decks.html. The token values are in design-system.html.

Scope

In this feature

  • A Settings dialog, opened from a Settings button at the bottom of the board rail. It has no Cancel. A change applies at once. Done and the close button close it.
  • Mode: Dark or Light. Light turns all chrome, the canvas ground and the dot grid light. Chrome means the top bar, the rail, dialogs, panels, the card strip, the zoom strip and the board list. Cards, notes, the Hook Card, connector badges and the 11 deck colors look the same in both modes.
  • Theme color: Orange, Blue or Green. It replaces the accent everywhere the accent marks an action or a selection. That covers the app mark, primary buttons, the selection outline, focus outlines, drop targets, slot hints, toggles, the Hook Card border, the rail Hook Card button and the genre counts.
  • A fixed warning color, split out from the old --accent-text. Warning text, the warning icon, "Save failed" and the Discard label use it in every theme color.
  • Snap to grid: on or off. With snap on, a dropped free card or note puts its top-left corner on the nearest 24 px grid dot. Alt held at the drop places it freely. A tucked card keeps its normal tuck place under its parent card. A note resize is always free.
  • A Keyboard list: R, Shift+R, Ctrl+Z and Ctrl+Shift+Z with their actions
  • A footer: "GameIdea <version> · No account. No data leaves this computer." The version comes from package.json.
  • Defaults for a new browser: Dark, Orange, Snap on
  • Settings saved in browser local storage, for each address and port. Other open tabs update at once.
  • A one-line note in the dialog when local storage is blocked
  • Rail: an Add note button. It places a new note at the free 24 px grid spot nearest the center of the view, opens it ready to type, and is one undo step.
  • Rail: the Genres button shows the number of genres on in the board row, for example "3 genres", or "All genres" when all 21 are on.
  • Rail: each of the 4 genre-tagged deck buttons shows its number of genres on. The count is hidden when all 21 are on. It replaces the "small mark" in the MVP plan.
  • M1 guard: no chrome color is written outside the design tokens. A lint check finds hex and rgba values in CSS modules.

Deferred

  • A "System" mode that follows the operating system setting
  • More theme colors than Orange, Blue and Green
  • A Settings button on the board list screen
  • Settings that go with the user to another browser or device

Never

  • A grid size setting. The grid stays at 24 px, because the placement rules (the 24 px margin and the 288 px "beside the card" spot) depend on it.
  • Snap that moves items already on the board when the user turns it on
  • Settings stored in a board record, a board file or the text export
  • Settings changes in the undo history
  • Card faces that change with Mode or Theme color

If the feature is wrong, the worst case is unreadable chrome in one mode or color, or cards that land on the wrong spot. No board data is at risk.

Data model changes

Board data does not change. One new record lives in local storage, outside the board database.

Settings                  (local storage key "gameidea.settings", one per address and port)
  version: 1
  mode:    dark | light               default dark
  accent:  orange | blue | green      default orange
  snap:    boolean                    default true

Rules

  • A missing record, a field with an unknown value, or JSON that does not parse gives the default for that field. It does not cause an error.
  • Each change writes the whole record.
  • The settings never go into a BoardRecord, a board file or the text export.
  • The settings are not in the undo history.

Migration and rollback

No boards exist, and the board format does not change, so there is no migration. A later change to Settings raises version. An unknown version is read field by field with the defaults rule. Rollback means removing the feature. A leftover local storage key does no harm.

Interfaces and contracts

Storage seam additions

shared/storage
  loadSettings()                        → Settings   (synchronous, defaults on any fault)
                                          and whether the browser can save settings
  saveSettings(settings)                → done or blocked
  onSettingsChangedElsewhere(handler)   called with Settings when another tab saves

Theme contract

<html data-mode="dark|light" data-theme="orange|blue|green">

The app sets these 2 attributes before the first render. All chrome colors come from tokens that the 2 attributes select. Card, note, badge and deck tokens do not depend on them.

Snap contract

  • Snap runs only on the drop of a free card or a note. A free card is a card that is not tucked and not on top of another card.
  • The top-left corner goes to the nearest multiple of 24 on each axis, in canvas coordinates. It uses the existing GRID constant in features/canvas/.
  • Alt held at the drop skips snap.
  • A drop that makes a tuck, a combine or an On Top uses those rules, and snap does not apply.
  • A drop is one undo step, with or without snap.

Rail

Top to bottom: Hook Card, Core, Modifiers, Optional, Genres (with its count line), Add note, and Settings at the bottom.

Architecture fit

Outcome 2: it fits, with one local exception.

It leans on these decisions in architecture.html:

  • state-store: the settings store is a second Zustand store, with no zundo.
  • architecture-pattern and module-layout: features/settings/ is a new feature folder in the existing pattern.
  • import-rules: canvas and the rail reach settings only through features/settings/index.ts. Only shared/storage/ touches browser storage.
  • undo-history: unchanged. Settings stay out of it, like a genre change.
  • nfr-targets: local storage makes no network request, so the privacy test still holds.

Local exception. It departs from storage-seam (moderate to reverse). The seam grows from 5 board actions to 8, with the 3 settings actions above. Local storage is used because it reads at once, so a Light user never sees a dark frame at load. IndexedDB reads arrive too late for that. If more kinds of browser preferences join the seam, the 5-action rule stops being true. Then /dev-architecture should split the seam into board actions and preference actions. docs/architecture.html is not edited for this exception.

Compatibility and rollout

No boards or users exist, so there is no data to keep and no flag. Turning snap on moves nothing that is already on the board. Each port keeps its own settings, the same as its boards, so development at 5174 does not change the settings at 4174.

Testing and regression plan

Unit tests (Vitest)

  • Settings parsing: a missing record, bad JSON and unknown values all give the defaults, field by field.
  • Snap math: the nearest 24 px point, negative coordinates, and the Alt bypass.
  • Snap does not apply to a tuck, combine or On Top drop.
  • Genre counts: the board row count, a count for each deck, hidden at 21, and "All genres".
  • Add note placement uses the free-spot rule.

Browser tests (Playwright, 3 engines)

  • Mode and Theme color on both screens. Each of the 6 combinations renders with no hard-coded chrome color.
  • Cards, notes, badges and the Hook Card are the same in every combination.
  • Warning text, "Save failed" and Discard keep the fixed warning color in Blue and Green.
  • A reload keeps the settings. A Light reload shows no dark frame.
  • A second tab updates in less than 1 second.
  • Blocked local storage gives the defaults and the note.
  • Add note.

Regression

  • The existing drag, tuck, combine and On Top tests run with snap on and with snap off.
  • The speed, size and privacy tests in nfr-targets still pass.
  • The M1 lint check runs on each pull request.

Open risks and assumptions

Risks

  • Card contrast in Light mode. The cards were designed for a dark table. On a light ground they can lose their edge. Resolved 2026-11-02: the card face is only 1.07:1 against the light canvas, so --shadow-card alone sets the edge. It reads clearly in the light mockups. The shadow stays as it is and must not be softened.
  • Accent contrast. Blue and Green must pass contrast on both a dark and a light ground, as fills and as text. Resolved 2026-11-02: fills with dark text pass (5.1 to 6.3:1), accent text passes in both modes, and dark-mode outlines pass. Light-mode outlines in --accent fail (2.4 to 2.9:1), so in light mode the selection and focus outlines use the light --accent-text.
  • The Keyboard list can drift from the real key handlers. A browser test checks that each listed key does what the list says.
  • Hard-coded colors added after M1 break Light mode. The lint check guards this.

Assumptions

  • The mockups were final-ish. /dev-ui-update settled text and spacing on 2026-11-02 in design-system.html.
  • The Keyboard list shows Ctrl. Cmd also works on a Mac, as in TheForge. The list does not show Cmd.
  • The footer shows the package.json version as it is, with no build number.
  • The mockups are in the repo at docs/design-handoff/.
