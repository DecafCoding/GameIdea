Architecture — GameIdea (working name)

Written 2026-11-01 from the /dev-architecture run. It serves docs/mvp-plan.html.

The user asked to follow the TheForge architecture unless there is an issue. TheForge is the user's story-card app, and GameIdea starts from a copy of its code. This document states every decision in full, so it does not depend on the TheForge documents.

Context

This design serves the MVP in docs/mvp-plan.html. The MVP is a canvas web app for solo and hobby game developers. The user draws game concept cards from 11 decks, rotates each card to choose a cue, tucks cards under a Hook Card, and copies the hook sentence.

Inherited constraints

  • The app runs in the browser only. There is no server code and no database server.
  • The app runs locally at fixed ports: 5174, 4174 and 4444. A public site is deferred.
  • The cost is $0 for each month.
  • The boards save to browser storage. The board file export is the only backup.
  • The cue pools are JSON data files, one for each deck. They come from one split of docs/libraries/decks.json, and the JSON is then the source.
  • Only Mechanic, Resource, Progression and Constraint carry genre tags. There are 21 genres and no generic tag. Each genre has at least 10 cues in each tagged deck.
  • The app runs on the current Chrome, Edge, Firefox and Safari on desktop.
  • A draw, a rotate or a Hook Card update takes less than 100 ms. The canvas moves smoothly with 200 cards. The first load takes less than 2 seconds.
  • There are no external services: no sign-in, no usage data and no AI.
  • Undo lasts for the open session only.
  • The library versions match TheForge exactly.

The market-wide signal in docs/competitive-scan.html about saving behind an account is answered by these constraints: local storage, no account, no cost.

Stack

Language and build: TypeScript with Vite

TypeScript 6.0.3 in strict mode. Vite 8.3.5 builds the app into static files, with @vitejs/plugin-react. Node.js 24 LTS runs the build tools only. npm installs the libraries. All versions are pinned exactly in package.json.

Override of the house default. The house default is C# with .NET. In a browser-only app, that means Blazor WebAssembly. The browser must first download the .NET runtime, which is several megabytes. That puts the 2-second first-load target at risk. The MVP plan also starts GameIdea from a copy of the TheForge TypeScript code. The user chose this stack in this run.

UI framework: React 19

React 19.3.1 and React DOM 19.3.1. The copied TheForge code uses React.

Canvas: React Flow 12

@xyflow/react 12.12.0 gives pan, zoom, drag and selection. A child node can belong to a parent node and move with it, which matches tuck. Cards are normal HTML. Only features/canvas/ imports it.

App state and undo: Zustand 5 with zundo

Zustand 5.0.16 holds the state of the open board. zundo 2.3.0 adds undo and redo. The storage module watches the store for autosave.

Test and code tools

  • Vitest 5.0.5 runs unit tests.
  • Playwright 1.64.1 runs browser tests in Chromium (Chrome and Edge), Firefox and WebKit (Safari).
  • ESLint finds code errors. Prettier keeps one code format. Their versions match TheForge.

Import checks: Zod 4

Zod 4.6.7 checks an imported board file against a schema. Only features/export/ uses it.

Fonts: bundled

@fontsource/inter 5.3.0 and @fontsource/space-grotesk 5.3.0. The fonts ship in the app files. The app loads no remote font.

Screens: address hash, no router library

The app has 2 screens. The board list is at #/. A board is at #/board/{id}.

Storage

Storage engine: IndexedDB with Dexie 4

IndexedDB is the browser's built-in database. Dexie 4.4.7 makes it easy to use and gives schema versions. The database name is gameidea, which keeps it apart from TheForge.

Persistent storage request

At start-up, the app asks the browser for persistent storage. This lowers the risk that the browser deletes the data. If the browser says no, the app works as normal.

Schema: one record for each board

Dexie database "gameidea"
  boards      key: id      one record for each board (BoardRecord)
  boardIndex  key: id      index: updatedAt   (id, name, createdAt, updatedAt)

BoardRecord
  formatVersion            starts at 1
  id, name, createdAt, updatedAt
  view:   { panX, panY, zoom }
  genres: { mechanic, resource, progression, constraint: Genre[] }
  cards:  Card[]           (see docs/mvp-plan.html, Data model)
  notes:  Note[]

Each save writes one board record and its index row.

Board file format: the BoardRecord as JSON

The board file is the BoardRecord as JSON, with its formatVersion. The file name is <board-name>.gameidea.json.

The format starts at version 1. The copied TheForge upgrade steps (versions 1 to 5) are removed, because they upgrade story boards. The upgrade mechanism stays: a later format change adds one step that changes one version into the next. Saved files must always load.

Cue pools: 11 JSON files from one split

public/pools/role.json          public/pools/setting.json
public/pools/mechanic.json      public/pools/mood.json
public/pools/goal.json          public/pools/twist.json
public/pools/conflict.json      public/pools/progression.json
public/pools/resource.json      public/pools/constraint.json
public/pools/modifier.json

Pool file
  type
  cues: { id, text, genres? }[]
    genres: present in mechanic, resource, progression and constraint only.
            One or more of the 21 genres. A cue that fits every genre lists all 21.
    targets: present in modifier only, and required there.
             One or more of role | resource | setting.

A one-time split makes these files from docs/libraries/decks.json. The split:

  • maps each deck name in decks.json to its pool file,
  • copies card into text without change, except for 2 grammar rules: it lowercases the first word of each Constraint cue ("No combat" becomes "no combat"), and it drops a leading "the", "a" or "an" from each Setting cue, because the Setting badge already ends in "the",
  • maps the genre names in genres.json to their kebab-case values, and stops with an error if it finds any or an unknown genre name,
  • stops with an error if any of the 21 genres has fewer than 10 cues in Mechanic, Resource, Progression or Constraint,
  • drops the games lists, because they hold game titles, which the plan bans in cues,
  • copies targets on Modifier cues (the card types a modifier fits: Player Role, Resource, Setting) into the modifier pool,
  • gives each cue a stable id.

Amended 2026-11-02. The Modifier deck draws as 3 decks: Role, Resource and Setting. All 3 read modifier.json. A draw uses only cues whose targets include the button's deck, the same way the genre filter works in the 4 genre-tagged decks. A modifier with more than 1 target is in more than 1 deck and is stored once. The file count stays at 11. The split now also:

  • maps the target names "Player Role", "Resource" and "Setting" to role, resource and setting, and stops with an error on an unknown target or an empty target list,
  • stops with an error if any of the 3 Modifier decks has fewer than 20 cues. A unit test checks the same floor on the pool files.

Targets guide the draw only. Any modifier can merge with any Player Role, Resource or Setting card. The reason for one file: the user asked why targets should work differently from genre tags, and no reason was found. 3 separate files would store a modifier up to 3 times and need a sync test. See feature-modifier-decks.html.

After the split, the pool files are the source, and the user edits them directly. decks.json and the Markdown libraries stay in docs/libraries/ as a record. No build step reads them. The app loads the pools by web address. A later server can serve the same addresses.

Test data: fixture boards

Tests use small fixture boards, plus one 200-card fixture board for the speed checks and one 11-card stack fixture for the long-stack test. A fixture is fixed test data.

Architecture pattern

Pattern: feature folders (Vertical Slice)

This is the house default, in its usual React form. Each feature has one folder. The folder holds the feature's screen parts, state actions, logic and tests. Shared code goes to shared/ only for genuine cross-cutting needs. The house default is kept, so it needs no override note.

Unit tests sit beside the code that they test, as *.test.ts or *.test.tsx.

Changes from the copied TheForge code: hook/ and genres/ are new. card/ gains the lock and loses the Setting kinds (place, object, event) and their icons. canvas/ replaces the story connector rules, including the rules based on Setting kind. draw/ gains the grouped rail and the genre filter for 4 decks.

Import rules

  • app/ can import features/ and shared/.
  • A feature can import shared/. It uses another feature only through that feature's index.ts file.
  • shared/ never imports features/ or app/.
  • Only shared/storage/ touches IndexedDB or Dexie.
  • Only features/canvas/ imports React Flow.
  • Only features/export/ imports Zod.
  • Only features/hook/ calls the Clipboard API.

Hook sentence builder: a pure function

The sentence builder in features/hook/ is a pure function. A pure function gives the same output for the same input and changes nothing else. It takes the stack as data (the cards in reading order, with their active cues and connector words) and returns the text. It does not import React Flow, so it can be unit-tested alone. The canvas gives it the stack in reading order. The rules are in docs/mvp-plan.html, Hook sentence rules.

Boundaries

Storage seam: 5 actions

shared/storage
  listBoards()                       → board index rows
  loadBoard(id)                      → BoardRecord
  saveBoard(record)                  → done or error
  deleteBoard(id)                    → done or error
  onBoardChangedElsewhere(handler)   called with a board id

The rest of the app uses only these 5 actions. A later server replaces only the inside of this module.

BroadcastChannel is a browser feature that lets tabs of one site send messages to each other.

Clipboard: write, with a dialog fallback

Copy on the Hook Card writes the sentence as plain text with the Clipboard API. The browser allows this only on a secure page and after a user action. Ports 4174 and 5174 on localhost and port 4444 over HTTPS are secure pages. If the write fails, the app shows the sentence selected in a small dialog, so the user can press Ctrl+C.

Pool load failure: error with a Retry button

If the pool files do not load, the app shows an error with a Retry button. Boards still open, and saved cards still show, because each card keeps a copy of its cues. Only the deck buttons stop. The pools come from the same place as the app, so they almost always load.

State and failure

Save: one transaction after each finished change

  • A save runs after each finished change. A drag saves once, when the card is dropped.
  • Each save writes the board record and its index row in one Dexie transaction. A transaction is a group of writes that all succeed or all fail.
  • A failed save leaves the last good version in place. The app shows a warning and offers an export.
  • A small mark shows when a save is waiting or has failed.
  • A genre setting change saves like any other change.

2 tabs: message, reload and warning

After a save, the tab sends a BroadcastChannel message with the board ID. Another tab that shows that board reloads it. It shows "This board changed in another tab" and clears its undo history. That tab loses changes made before the reload.

Undo: up to 100 steps for each board, for the session

  • Each board has its own undo history of up to 100 steps. The history clears when the user changes boards or reloads the page.
  • Discard deletes a card, and undo brings it back.
  • Redraw All is one undo step. Undo brings back every card it replaced.
  • Lock and unlock are each one undo step.
  • A genre setting change is kept out of the undo history. It is a setting for the next draw, and an undo step the user cannot see on the canvas is confusing.

Format upgrades

IndexedDB uses Dexie schema versions. A board file with an old formatVersion goes through the upgrade steps on import. GameIdea starts at version 1 with no upgrade steps.

Import: always a new board

  • A good import always makes a new board with a new ID. It never writes over a board that exists.
  • If the name is already used, the app adds "(imported)" to the new name.
  • A bad file fails the Zod check. The app shows a message, and nothing changes.

There is no concurrency between users, because there is only one user and no server.

Deployment

Run target: local, fixed ports

CommandAddressUse
npm starthttp://localhost:4174Builds the app and serves it. This is the user's real work.
npm run devhttp://localhost:5174Development, with live reload.
npm run start:lanhttps://<LAN address>:4444The same build over HTTPS for other devices on the local network. Each device keeps its own boards.
  • All 3 ports are locked. If a port is in use, the command stops with an error. It does not move to another port.
  • The ports differ from the TheForge ports (5173, 4173, 4443), so both apps can run at the same time.
  • Port 4444 uses a certificate from mkcert, kept in .certs/ and ignored by git. mkcert is a tool that makes a certificate the local computer trusts. GameIdea has its own copy of the certificate files. HTTPS makes the page a secure context, so persistent storage and the Clipboard API work.
  • Port 4174 stays plain HTTP on localhost, because https://localhost:4174 would be a different site and would hide the user's boards.
  • The browser stores boards for each address and port. The boards on port 4174 are separate from the boards on port 5174, so development does not touch the user's real work.
  • The app has no configuration and no secrets.
  • A public static site is deferred. The same build output can go to a free host later.

Source control: git and GitHub

The repository is ~/repos/gameidea, pushed to the GitHub repository DecafCoding/GameIdea. The build pipeline needs it, because /dev-execute opens and merges pull requests.

CI: GitHub Actions on each pull request

CI means continuous integration, which runs the checks automatically. On each pull request, GitHub Actions runs lint, type checks, unit tests, Playwright tests and the size checks. A failed check blocks the merge. The CI needs no secrets, because nothing deploys.

The biggest risks

  • Story code left in the copy. TheForge code names 5 story types, Setting kinds and kind-based connector rules in many places. Code left behind causes odd bugs in later phases. Check: the M1 pass bar adds a search of src/ that finds no TheForge story type names (character, motivation, description) and no Setting kind names.
  • Long stacks. A full hook stack is 6 to 11 cards in one parent chain. TheForge tested tuck with short stacks. Check: M2 starts with the 11-card stack test in nfr-targets. If it fails, features/canvas/ lays out the stack itself, which is an amendment to canvas-library.
  • Lost browser data. The persistent storage request and the export lower this risk. They do not remove it.
